# Production on K3s

Docker Compose remains the local workflow. Production uses **CloudNativePG from
the first node**, not the Compose PostgreSQL container.

Start with [the deployment runbook](../../docs/k3s-deployment.md), then read
[operations](../../docs/kubernetes-operations.md),
[backup/recovery](../../docs/backup-and-recovery.md), and the
[readiness report](../../docs/kubernetes-readiness-report.md).

| Directory | Responsibility |
| --- | --- |
| apps/base | shared config/account, web/API Services and Deployments, one worker/PVC, Traefik Ingress/Issuer |
| apps/overlays/single-node | one web, one API, one worker |
| apps/overlays/ha | two web/API with spreading/PDBs; still one worker |
| database/base | CNPG PostgreSQL16/PostGIS Cluster, Barman ObjectStore, daily backup |
| database/overlays | one or three CNPG instances; same stable RW endpoint |
| migrations | dedicated privileged, atomic schema migration Job |
| maintenance | explicit bootstrap, analytics and model Jobs |
| security | namespace, restricted pod policy, ingress NetworkPolicies |
| addons | pinned prerequisites and deliberate upgrade instructions |
| cache | optional Redis contract and future Sentinel architecture; no deployed Redis |
| scripts | phase-specific operator helper; schema and disposable-K3s tests |

The namespace is `real-estate`; the database Cluster is `real-estate-db`, and
applications use `real-estate-db-rw.real-estate.svc.cluster.local`.

## Do not bootstrap with one apply

Required order: prerequisites → namespace/secrets → database → Ready →
configuration → migrations Job → Complete → bootstrap Job → Complete → explicit
models Job if required → API Ready → web Ready → ingress → scheduled worker.
The runbook provides each command and verification gate.

`make k8s-apps-apply-single` / `make k8s-apps-apply-ha` are **subsequent rollout**
helpers, not fresh-install orchestration. Image/host placeholders deliberately
cannot be deployed through the helper. Real Secrets are never generated by
Kustomize or tracked here.

Render without a cluster:

```sh
make k8s-render-single
make k8s-render-ha
kubectl kustomize infrastructure/kubernetes/apps/overlays/single-node
kubectl kustomize infrastructure/kubernetes/apps/overlays/ha
kubectl kustomize infrastructure/kubernetes/database/overlays/single-node
kubectl kustomize infrastructure/kubernetes/database/overlays/ha
```

Validation tooling uses a development-only Python environment with
`scripts/requirements.txt`; operators need only kubectl and a POSIX shell for
the convenience script (or render/apply Kustomize directly). On Windows use WSL
or Git Bash for shell examples, or equivalent native kubectl commands.

There is no destructive Make target. Deleting a namespace/Cluster/PVC can destroy
data, and removing a Job cannot undo SQL that has committed.
